# Политика безопасности

## Основная модель: GitVerse Pages + Яндекс Диск

GitVerse Pages публикует только статический код, и по требованиям сервиса репозиторий публичный. Реальные рецепты, фотографии, черновики и очереди операций не встраиваются в сборку и не отправляются в GitVerse.

Семейные данные хранятся в папке конкретного OAuth-приложения на Яндекс Диске. Запрашивается единственное право `cloud_api:disk.app_folder`; приложение не получает чтение или запись остальных файлов пользователя.

- `ClientID` публичен по устройству OAuth и может находиться в `public/runtime-config.js`.
- OAuth access token является секретом: он хранится только в IndexedDB устройства.
- Token не выводится в логи, URL после завершения входа очищается через `history.replaceState`.
- OAuth callback проверяет случайный `state`, сохранённый в `sessionStorage`.
- Redirect URI должен точно совпадать с HTTPS-адресом приложения.
- Content Security Policy запрещает загрузку стороннего JavaScript.
- Service worker получает токен только из той же origin-scoped IndexedDB и использует его для загрузки приватного изображения.
- При отключении облака token удаляется; локальная книга не уничтожается.

Посетитель публичного URL не получает доступ к семейной книге: без входа он видит только локальную копию/демо, а после входа — папку приложения собственного Яндекс-аккаунта. Для одной общей книги разрешённые устройства должны использовать один выбранный семейный аккаунт.

## Резервная модель: ChatGPT Sites/D1/R2

Production-сайт должен оставаться приватным. Платформа аутентифицирует посетителя и передаёт серверу стабильный `oai-authenticated-user-id`; браузер не может назначить себе участника через тело запроса.

Первый разрешённый посетитель создаёт книгу и становится `owner`. Следующие посетители, которых заранее допустила приватная политика Site, добавляются как `editor`. Роль `viewer` предусмотрена моделью и блокируется в `assertEditor` для любых изменений.

Если сайт станет публичным, автоматическое добавление редакторов в `ensureBook` необходимо заменить явным allowlist или экраном приглашений. До этого переключать audience на public нельзя.

## Серверные гарантии

- D1 и R2 подключены только как Worker bindings; публичного database URL или storage token нет.
- `/api/snapshot` выдаёт записи только книги, найденной через `book_members`.
- `/api/operations` и `/api/images` требуют аутентификацию и проверяют `Origin` для изменяющих запросов.
- Все update/delete/select ограничены `book_id`; идентификаторы рецептов и изображений дополнительно проверяются на межкнижные коллизии.
- R2 bucket приватный. `/api/images/:id` сначала проверяет членство и связывает `image.id` с той же книгой.
- Загрузка принимает только JPEG, PNG, WebP и AVIF; основное изображение ограничено 4,5 МБ, thumbnail — 1 МБ, весь запрос — 8 МБ.
- Пакет операций ограничен количеством и размером. На сервере повторный `opId` не применяется второй раз.
- SQL выполняется prepared statements; пользовательские значения не интерполируются в запросы.
- Ответы с личными данными помечены `private, no-store`; MIME sniffing отключён.

## Почему нет RLS-файла

Cloudflare D1 не предоставляет PostgreSQL Row Level Security и не выдаётся клиенту как публичный Data API. Эквивалентная политика реализована в серверном шлюзе `server/auth.ts` и `server/book-store.ts`: сначала членство, затем обязательный `book_id` в каждом запросе. Открытых правил наподобие `allow read, write: if true` в проекте нет.

## Секреты

В репозитории не должно быть:

- source-write credentials Sites;
- Cloudflare API tokens;
- cookies или access tokens;
- реальных `.env` файлов;
- публичных R2 credentials.
- OAuth access tokens Яндекса.

Yandex OAuth `ClientID` не является секретом. Не путайте его с access token.

`.gitignore` исключает `.env*`, разрешая только безопасный `.env.example`. Перед публикацией полезно выполнить:

```bash
rg -n "API_KEY|SECRET|TOKEN|PRIVATE_KEY|BEGIN RSA|BEGIN OPENSSH" . \
  -g '!node_modules/**' -g '!package-lock.json'
```

## Реакция на инцидент

1. Скачать полный ZIP, если доступ к данным ещё есть.
2. При утечке Yandex token отозвать доступ приложения в настройках Яндекс ID и подключить устройства заново.
3. При утечке Git credential заменить его; пользовательских данных в Git быть не должно.
4. Для резервного Sites backend сразу перевести Site в owner-only/private, отозвать credential и проверить `book_members`.
5. Создать и проверить исправленную версию до повторного подключения облака.

Резервные ZIP-файлы содержат семейные тексты и фотографии. Храните их как личные документы и не отправляйте в публичные репозитории.
